PART 1

Starting Simple: What Migration Means

Slides 3/37 – 6/37

Where We Are & Today's Question

Slide 3/37

From the Last Session:

  • Cloud computing means using computers someone else owns, over a network, paying for what you use.
  • Service models decide how much of the system you run yourself: IaaS, PaaS, SaaS.
  • A cloud machine is an image, a size, storage, and network rules. Containers are a lighter alternative.
Today's Question: An organization already has systems running in its own building. They work. People use them every day. How do you move them to the cloud without breaking anything?

A Comparison You Already Understand: Moving House

Slide 4/37

Before you move house, you:

1. Make a list
Make a list of everything you own ➔ Inventory
2. Decide fate
Take as it is, repair first, replace, or throw away ➔ The "R"s
3. Check new place
Check rooms, power, internet ➔ Requirements & Capacity
4. Choose a day
Avoid the week of your exams ➔ Quiet window, not busy period
5. Test first
Test the new place before giving back keys to the old one ➔ Test & Rollback ready

Cloud migration is the same list, applied to computer systems.

What Cloud Migration Means & Core Vocabulary

Slide 5/37
Cloud migration: moving applications, data, and machines from where they run now to a cloud — or from one cloud to another.
Visualizing the 4 Core Migration Terms (Slide 5/37)
SOURCE (Where it is now)
Current Environment
📦 Workload: Application + Machines + Data + Settings
1. Copy & Migrate Workload ───►
2. CUTOVER: Switch Users ───►
◄─── 3. ROLLBACK (if new system fails)
TARGET (Where it is going)
Cloud Environment
☁️ Workload: Application + Machines + Data + Settings
  • Workload — one application together with everything it needs to run: its machines, its data, its settings.
  • Source and target — where the workload is now, and where it is going.
  • Cutover — the moment users are switched from the old system to the new one.
  • Rollback — going back to the old system when the new one fails.

Why Organizations Migrate — and Why Some Do Not

Slide 6/37

✅ Common Reasons to Move

  • Old hardware must be replaced anyway
  • The data center lease or contract is ending
  • Demand changes a lot during the year
  • The company wants to stop running buildings and servers

🛑 Common Reasons to Stay

  • Laws require data to stay in a specific place
  • The system is very old and nobody understands it
  • The hardware is new and already paid for
  • Moving costs more than it would save

Not every system should move. Deciding which ones should, and how, is what migration planning is for.

PART 2

Planning a Migration

Slides 7/37 – 14/37

The 5 Phases of a Migration

Slide 7/37
PHASE 1
1. Assess

Find out what you have, what it depends on, and how well it runs today.

PHASE 2
2. Plan

Choose a strategy for each workload, an order, and dates.

PHASE 3
3. Migrate

Build the target, copy the data, move the workload.

PHASE 4
4. Test & validate

Prove the new system works before users arrive.

PHASE 5
5. Operate & improve

Run it, watch it, and adjust size and cost.

📌 Provider Naming Note: Providers use different names for these phases (AWS: assess, mobilize, migrate; Microsoft: prepare, assess, deploy, release), but the order is always the same.

Assessment: Know What You Have

Slide 8/37

Before moving anything, collect:

📋 Inventory — every server, application, database, and the software licenses they use.
🔗 Dependencies — what each workload needs in order to work: other servers, databases, shared folders, login systems.
📊 Baseline — measurements of how the system performs today: processor and memory use, response time, number of users. You will compare the new system against these numbers.
⚖️ Requirements — rules the new location must meet: security, laws about data, and how long the system may be unavailable.
⚠️ Most failed migrations fail here, because something was never written down.

Dependencies: The Hidden Part & Migration Waves

Slide 9/37
Example Dependency Chain: Student Registration System (Slide 9/37)
1. Web Server
Students open in their browser
2. Database Server
Web server reads from database
3. University Login System
Checks student passwords
4. Shared Folder
Writes reports for finance office
❌ What happens if you move ONLY the web server? It will be slower (every request now crosses the internet to reach the database) or it will stop working completely (a firewall blocks the connection).
Rule: Workloads that depend on each other are usually moved together, in the same migration wave — a group of workloads moved at the same time.

Is It Worth It? Counting the Full Cost (TCO)

Slide 10/37

Total cost of ownership (TCO): everything a system costs over its life, not only the price of the machines.

🏢 Staying in your own building ☁️ Moving to the cloud
Servers, storage, network equipment Monthly bill for machines and storage
Electricity, cooling, building space Charges for data leaving the provider
Staff time for repairs and updates Staff time to learn new tools
Replacing hardware every few years One-time cost of the migration itself

Compare both columns over the same period, usually three to five years. Every provider offers a free calculator for this.

Migration Strategies: The "R"s (6 R's + 7th Relocate)

Slide 11/37
Strategy What you do Example
Rehost Move it as it is onto cloud VMs (lift and shift). Copy a web server VM to the cloud unchanged.
Replatform Move it with small changes that use a cloud service. Use the provider's managed database instead of your own.
Refactor Redesign and rewrite it for the cloud. Split a large program into containers.
Repurchase Replace it with a SaaS product. In-house email server ➔ Microsoft 365.
Retire Switch it off; nobody needs it. A tool nobody has opened in two years.
Retain Keep it where it is, for now. A system that laws require to stay in-house.
➕ The 7th "R": AWS adds a seventh, relocate: moving a whole virtualization platform to the cloud without changing the machines on it.

Choosing a Strategy: Speed & Low Risk vs. Long-Term Benefit

Slide 12/37

The strategies trade speed and low risk against long-term benefit:

Rehost (Lift & Shift) Fastest / Low Risk
  • Fastest and cheapest to do
  • Least risk of breaking the application
  • Gains little: the same system, now renting instead of owning
Refactor (Cloud-Native Redesign) Highest Long-Term Benefit
  • Slowest and most expensive to do
  • Highest risk during the change
  • Gains the most: elasticity, managed services, lower running cost
💡 A common path: rehost first to leave the data center on time, then replatform or refactor the important systems once they are running in the cloud.

Worked Exercise: Choose a Strategy for Each Workload

Slide 13/37
1. A timesheet application on its own server, which works well, and the data center closes in three months.
1 ➔ Rehost (Fast deadline; works as-is)
2. A company runs its own email server, and two staff spend half their time keeping it working.
2 ➔ Repurchase (Replace with SaaS email)
3. A reporting tool whose last login was eighteen months ago.
3 ➔ Retire (Unused; switch it off)
4. An online shop that slows down every holiday season and must grow and shrink automatically.
4 ➔ Refactor (or replatform) (Needs cloud elasticity)
5. A laboratory system connected by cable to a physical measuring device.
5 ➔ Retain (Tied to local hardware)

📌 Slide Note: The reason matters more than the label.

Timing: When to Move

Slide 14/37
  • Start with a pilot — one small, low-risk workload, moved first, to learn the process before anything important is touched.
  • Move in waves — groups of related workloads, one group at a time, never everything at once.
  • Choose quiet times — nights, weekends, or holidays when few people use the system.
  • Avoid busy periods — no university moves its registration system during registration week.
  • Leave time to go back — plan the cutover so that a rollback is still possible if the tests fail.
PART 3

Carrying Out the Migration

Slides 15/37 – 22/37

Change Management (5 Controlled Steps)

Slide 15/37

Migration changes systems people depend on. Change management is the process that keeps those changes controlled:

1. Request
Write down what will change, why, when, the risk, and how to undo it.
2. Approve
The people responsible (often a change advisory board) agree to it.
3. Announce
Tell users when the system will be unavailable.
4. Carry out
In the agreed time slot, called a maintenance window.
5. Record
Write down what happened, including anything that went wrong.

Deployment Automation: Infrastructure as Code (IaC)

Slide 16/37

Building the target by clicking in a web console works for one machine. It does not work for two hundred, and nobody can repeat it exactly.

Infrastructure as code: describing machines, networks, and settings in text files, which a tool reads and then creates everything automatically.
🔁 Repeatable — run it again and get exactly the same result.
👀 Reviewable — colleagues can read and check the file before it runs.
📝 Recorded — every change is saved, so "what changed?" has an answer.

Common tools: Terraform (works with every provider), AWS CloudFormation, Azure Bicep. We return to this in the automation topic.

Moving Data: How Long Does It Take? (Formula & Calculation)

Slide 17/37

Data travels at the speed of your network connection. A quick calculation:

How to Calculate Transfer Time
bytes × 8 = bits
bits ÷ bits per second = seconds
Example (50 TB @ 1 Gbps):
50 × 10^12 × 8 ÷ 10^9 = 400,000 s ≈ 4.6 days
Amount of data 100 Mbps line (100%) 1 Gbps line (100%)
5 TB about 4.6 days about 11 hours
50 TB about 46 days about 4.6 days
⚠️ Realistic Throughput Rule: These assume the line is used at 100% the whole time, which never happens. At a more realistic 70%, 50 TB over 1 Gbps takes about 6.6 days.

Moving Data: Online or Offline Transfer

Slide 18/37

🌐 Online transfer

Copy over the network — the internet, a VPN, or a private line to the provider.

  • Simple, and can keep copying changes
  • Too slow for very large amounts

🚚 Offline transfer

The provider sends a physical storage device; you fill it and ship it back.

  • Fast for very large amounts
  • Days of shipping; no updates during that time
✅ A Common Combination (Hybrid Bulk + Delta Sync):

Send the bulk of the data offline (Step 1: physical appliance), then copy only the changes made since then over the network, just before cutover (Step 2: online delta sync).

Examples: Azure Data Box. The textbook also mentions AWS Snowball; since November 2025, AWS no longer offers it to new customers.

Moving Virtual Machines (P2V, V2V, V2C)

Slide 19/37

Three types of move, named by where the machine starts and where it ends:

🖥️ ➔ 📦 P2V (physical to virtual): turn a real server into a virtual machine.
📦 ➔ 📦 V2V (virtual to virtual): move a virtual machine to a different hypervisor.
📦 ➔ ☁️ V2C (virtual to cloud): move a virtual machine to a cloud provider.
🔧 What Makes It Harder Than Copying a File:
  • Each hypervisor stores virtual disks in its own format — VMDK for VMware, VHD for Microsoft, QCOW2 for KVM — so the disk may need converting.
  • The machine may also need new drivers to run on the new hypervisor.

Migration tools can copy a machine while it keeps running, then switch over in minutes at the end.

Moving Storage and Databases (Minimizing Downtime)

Slide 20/37

A database is in use while you copy it, so its contents keep changing. The usual 4-step method:

STEP 1 (Users Online)
Initial Full Copy

Copy everything while the old system keeps running.

STEP 2 (Users Online)
Ongoing Replication

Keep copying the changes as they happen.

STEP 3 (Brief Stop)
Stop & Final Sync

Stop the old system briefly, copy the last few changes.

STEP 4 (Live on Cloud)
Switch Users

Switch users to the new database.

⏱️ The time between steps 3 and 4 is the ONLY time users cannot work. Good planning makes it minutes instead of days.

⚠️ Cross-Engine Warning: Moving between two different database products (for example, from Oracle to PostgreSQL) is much harder than moving the same product, because the data types and features differ.

Moving From One Cloud to Another (Vendor Lock-In)

Slide 21/37

Everything on the previous slides still applies, plus three new problems:

  • Egress charges — the old provider charges for every gigabyte that leaves it.
  • Different services — a managed database or function service on one provider has no exact equal on the other, so some parts must be rebuilt.
  • Different tools and names — permissions, networks, and monitoring all work differently.
This is vendor lock-in from last session, now with a price on it. Workloads built on standard tools — virtual machines, containers, common databases — are much easier to move.

Cutover: Switching the Users (DNS & TTL)

Slide 22/37

Most systems are reached by a name, such as obs.aydin.edu.tr, not by a numeric address.
DNS (Domain Name System) is the internet's address book: it turns a name into the numeric address of a server. To switch users, you change the DNS entry to point to the new system.

Users' Browsers
obs.aydin.edu.tr
Caches answer for TTL duration
DNS Record
Lower TTL a day before cutover!
Old Server (Keep running until proven ➔ Rollback)
New Cloud Server (Cutover Target)
1️⃣ Two things to know (TTL): The switch is not instant: computers remember old DNS answers for a set time (the TTL, time to live), so lower it a day before cutover.
2️⃣ Rollback Safety: Keep the old system running until the new one is proven. Pointing the name back is your rollback.
PART 4

Testing Before Users Arrive

Slides 23/37 – 25/37

6 Types of Testing

Slide 23/37
Test The question it answers
Functional Does every feature still do what it did before?
Performance and load Is it as fast as the baseline, with a normal number of users and with many users at once?
Data validation Did every record arrive, complete and unchanged?
Security Are only the right people and ports allowed in? Is the data encrypted?
Regression Did fixing one thing break something that worked before?
User acceptance Do real users agree it is ready?

Deciding Whether the Test Passed

Slide 24/37
  • Decide the pass rule before testing — for example, "pages load in under two seconds for 500 users at once". Deciding afterwards invites excuses.
  • Compare with the baseline — the measurements taken during assessment. "Fast enough" means "at least as fast as before".
  • Test in a copy first — a separate environment that looks like the real one, never on the system users depend on.
  • If it fails — fix it and test again, or roll back. Never cut over and hope.

Common Problems After a Migration & Their Usual Causes

Slide 25/37
Problem Usual cause
The application cannot reach its database A firewall rule was not copied, or the database moved separately.
Everything works but is slow The machine is too small, or part of the system stayed behind and every request crosses the internet.
It works for some users and not others An address was written into the program instead of a name (hard-coded IP).
It stopped after a few days A software license was tied to the old hardware.
Times and dates are wrong The new machines use a different time zone.
Users cannot log in Permissions or the login system connection were not moved.
PART 5

Working in Small Steps

Slides 26/37 – 28/37

Two Ways to Run a Project: Waterfall vs. Agile

Slide 26/37

Waterfall

Plan everything first, then build everything, then test everything, then deliver once at the end.

  • Clear and predictable
  • Problems are found late, when they cost most to fix

Agile

Work in short cycles of one to four weeks. Each cycle delivers something small that works.

  • Problems are found early
  • Plans change as you learn

Migrating in waves, starting with a pilot, is the agile idea applied to migration: move a little, learn, then move more.

Where Changes Are Tried Before Users See Them (Environments & CI/CD)

Slide 27/37

Organizations keep separate copies of a system, called environments:

STEP 1
Development

Where programmers write and try changes.

STEP 2 (Passes Tests ➔)
Test (or staging)

A copy that looks like the real system, used for the tests in Part 4.

STEP 3 (Passes Tests ➔)
Production

The real system that users depend on.

A change moves from development to test to production, and only moves forward when it passes. Cloud makes this cheap: a test environment can be created for a day and deleted afterwards.

Doing these steps automatically every time the code changes is called CI/CD (continuous integration and continuous delivery).

Releasing Changes Safely: Blue-Green, Canary, and Rolling

Slide 28/37

Three common ways to release a new version without stopping the service:

1. Blue-green

Run two identical environments. Users are on one (blue); the new version goes on the other (green). Switch everyone at once, and switch back if needed.

BLUE (v1) — 100% ➔ 0%
GREEN (v2) — 0% ➔ 100%
2. Canary

Send a small share of users, say 5%, to the new version first. If nothing goes wrong, increase the share step by step.

Old Version (v1) — 95% users
🐤 Canary (v2) — 5% users
3. Rolling

Update the machines a few at a time, so some are always serving users.

v2
v2
v1
v1

🐤 Origin of "canary": Coal miners took a canary underground; if the bird got sick, the miners left before they did too.

PART 6

Planning for Problems: Capacity, RPO/RTO & Recovery Sites

Slides 29/37 – 33/37

Capacity: The Cloud Is Not Endless

Slide 29/37
  • Account limits (quotas) — every provider limits how many processors, machines, or addresses an account may use in each region. New accounts have low limits.
  • Regional shortages — a particular machine type can be sold out in a region, especially GPU machines.
  • Network limits — your own connection to the provider can become the slowest point.
📈 Capacity planning: Measure how use grows over time, estimate what you will need, and ask the provider to raise your limits weeks before a migration — not on the day, when the request can take days to approve.

Continuity and Recovery (BC vs. DR)

Slide 30/37

Business continuity

How the organization keeps working during a disruption: people, procedures, alternatives.
Example: staff take payments by hand while the system is down.

Disaster recovery

How the IT systems are brought back after a failure: backups, a second site, the steps to restore.

📌 Disaster recovery is one part of business continuity. A disaster does not need to be a fire or an earthquake — a deleted database or a failed region counts.

Two Numbers Every Recovery Plan Needs: RPO and RTO

Slide 31/37
Visualizing RPO (Past Data Loss) vs. RTO (Future Downtime)
◄─── RPO (Recovery Point Objective)
Last Good Backup ➔ Failure
How much data can we afford to lose? (Measured in time since last copy)
⚡ FAILURE EVENT
(System Goes Down)
RTO (Recovery Time Objective) ───►
Failure ➔ System Restored
How long can the system be unavailable? (Max allowed downtime)
  • RPO — recovery point objective: How much data can we afford to lose? Measured in time since the last copy. • RPO of 1 hour ➔ a copy is needed at least every hour.
  • RTO — recovery time objective: How long can the system be unavailable? • RTO of 4 hours ➔ it must be running again within 4 hours of the failure.
💰 The trade-off: Smaller numbers cost more. An RPO of zero means every change is copied to a second place instantly; an RTO of minutes means a second copy of the whole system is always running. Set them by how much the business loses per hour, not by what sounds best.

Recovery Sites: Hot, Warm, and Cold

Slide 32/37
Site What is ready Back in Cost
Hot A full copy of the system, running, with current data. Minutes Highest
Warm Machines and network ready but small; data copied regularly. Hours Medium
Cold Only the space, or in the cloud only the backups. Everything must be built. Days Lowest

💡 In the cloud, a cold site costs almost nothing while unused, because you pay only for stored backups. This is one of the strongest reasons to use the cloud for recovery, even for systems that stay in-house.

Worked Self-Check: Online Shop vs. School Library Catalog

Slide 33/37
Question: An online shop loses a lot of money for every hour it is down, and it cannot lose any order. A school's library catalog can be down for a day, and losing the last day of changes is acceptable. Give each a rough RPO, RTO, and recovery site.
🛒 Online Shop

• RPO: Close to zero
• RTO: Minutes
• Site: Hot site (Expensive, but cheaper than the losses).

📚 School Library Catalog

• RPO: One day
• RTO: One day
• Site: Cold site (daily backups in the cloud; almost free).

7-Point Lecture Summary

Slide 35/37
  1. Migration moves workloads to the cloud: assess, plan, migrate, test, operate.
  2. Most failures come from assessment: a dependency or a baseline nobody recorded.
  3. Each workload gets a strategy: rehost, replatform, refactor, repurchase, retire, or retain.
  4. Start with a pilot, move in waves, and keep a rollback ready.
  5. For large data, the network is the slowest part; calculate the time first.
  6. Test against the baseline with rules decided in advance.
  7. Every recovery plan needs an RPO and an RTO, and they decide the cost.
