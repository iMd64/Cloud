🏢 Own vs. Rent & On-Premises Operations

M1-2 Slide 8 M1-2 Slide 13
🏛️ Own (On-Premises Model)

On-Premises means the organization owns and runs everything itself. The organization purchases physical servers, leases or buys real estate, installs industrial cooling (HVAC), backup diesel generators, redundant network feeds, and employs 24/7 facilities and hardware maintenance engineers.

  • Financial burden: Massive upfront capital commitment (CapEx) with continuous physical maintenance.
  • Capacity limitation: Fixed hardware limits; excess capacity sits idle, while unexpected spikes crash the service.
  • Depreciation: Hardware depreciates over 3–5 years and requires costly refresh cycles.
☁️ Rent (Cloud Computing Model)

Rent means consuming infrastructure as an elastic service. Compute cycles, memory, and petabytes of disk are rented on-demand from a global hyperscaler (AWS, Azure, GCP) with zero hardware purchase.

  • Financial shift: Pay only for the minutes or seconds compute resources actively run (OpEx).
  • Operational agility: Spin up 1,000 servers in minutes; terminate them when done with zero lingering debt.
  • Maintenance offload: Power, physical cooling, firmware updates, and physical rack security are 100% provider obligations.

🖥️ Core Infrastructure Definitions: Server, Data Center, Virtualization, Hypervisor

M1-2 Slide 10
Server

A dedicated physical or virtual computing machine designed to process requests and deliver data, applications, or network services to other client computers over a network 24/7.

Data Center

A specialized physical building or industrial complex engineered with redundant power feeds, UPS battery arrays, backup diesel generators, environmental HVAC cooling, fire suppression, and biometric security to house thousands of server racks.

Virtualization

The fundamental technology that decouples software from physical hardware. It abstracts physical compute, RAM, storage, and networking into software-defined pools, allowing multiple isolated virtual systems to run on one physical host.

Hypervisor

Also known as the Virtual Machine Monitor (VMM). The low-level software or firmware layer that creates, runs, and isolates virtual machines while actively arbitrating access to the host's physical CPU cores, RAM, and PCIe buses.

📜 Official Cloud Computing Definition (NIST SP 800-145)

M1-2 Slide 12
“Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (e.g., networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction.”
— National Institute of Standards and Technology (NIST SP 800-145), Peter Mell & Timothy Grance

⭐ The 5 Essential Characteristics of Cloud Computing

M1-2 Slides 16–17

To be considered a true cloud under NIST standards, a platform must satisfy all 5 characteristics simultaneously:

1 On-Demand Self-Service

A consumer can provision computing capabilities (server time, network storage) automatically as needed without requiring human interaction with the cloud service provider's staff.

2 Broad Network Access

Capabilities are available over the network and accessed through standard mechanisms that promote use by heterogeneous thin or thick client platforms (mobile phones, tablets, laptops, workstations).

3 Resource Pooling

The provider’s computing resources are pooled to serve multiple consumers using a multi-tenant model, with physical and virtual resources dynamically assigned and reassigned according to consumer demand, with location independence.

4 Rapid Elasticity

Capabilities can be elastically provisioned and released, in some cases automatically, to scale rapidly outward and inward commensurate with demand. To the consumer, resources often appear unlimited.

5 Measured Service

Cloud systems automatically control and optimize resource use by leveraging a metering capability at some level of abstraction appropriate to the type of service (storage, processing, bandwidth, active user accounts). Usage can be monitored, controlled, and reported.

⚖️ Multi-Tenancy, Scaling Dimensions & Financial Models

M1-2 Slide 18 M1-2 Slide 19 M1-2 Slide 21
Multi-Tenancy (Slide 18)

In a multi-tenant cloud architecture, multiple distinct customer organizations (tenants) share the exact same underlying physical server hardware, network routers, and physical storage pools. The hypervisor and cloud management software strictly isolate each tenant's data, memory spaces, and network packets so that no tenant can inspect, disrupt, or access another tenant's workload.

Scalability (Scaling Up) vs. Elasticity (Scaling Out) — Slide 19 Crucial Midterm Distinction

Dimension Scalability (Vertical / Scale Up) Elasticity (Horizontal / Scale Out)
Definition Increasing capacity by adding more resources (vCPU, RAM, faster SSDs) to a single existing machine. Dynamically adding or removing multiple server instances behind a load balancer in response to real-time workload fluctuations.
Direction Vertical (Up / Down) Horizontal (Out / In)
Downtime Impact Usually requires VM reboot to re-size instance type or attach memory. Zero downtime; new instances launch in parallel and join the pool seamlessly.
Physical Ceiling Limited by the maximum motherboard capacity of the physical host. Practically limitless across the entire provider global fleet.
CapEx (Capital Expenditure) Slide 21

Money spent upfront on physical, tangible assets (racks, servers, SAN switches, building generators). Amortized over 3–7 years on balance sheets. Carries high forecasting risk: if you over-purchase, capital is wasted; if you under-purchase, systems fail under load.

OpEx (Operational Expenditure) Slide 21

Ongoing day-to-day business operational expenses. Fully deductible in the current tax year. Cloud operates on 100% OpEx: you pay only for compute seconds, consumed bandwidth, and active gigabytes, scaling costs down when traffic subsides.

🌐 Deployment Models & Public vs. Private Decision Matrix

M1-2 Slide 23 M1-2 Slide 24
Public Cloud

Owned and operated by third-party provider (AWS, Azure, GCP); open to general public/businesses over internet. Multi-tenant.

Private Cloud

Operated solely for a single organization. Can be hosted on-prem or by a 3rd party. Offers maximum data control and regulatory compliance.

Community Cloud

Shared by several organizations with shared concerns (e.g. healthcare compliance, defense agencies, state universities).

Hybrid Cloud

Composition of two or more distinct clouds (private + public) bound together by standardized technology enabling data/app portability.

Multi-Cloud

Using services from multiple independent public cloud vendors (e.g. AWS compute + GCP BigQuery analytics) to avoid vendor lock-in.

When to Choose Public vs. Private? (Slide 24 Decision Matrix)
Choose Public Cloud When:
  • Rapid time-to-market is the #1 priority.
  • Workload demand fluctuates wildly (unpredictable spikes).
  • Zero capital for upfront data center investment.
  • Organization wants zero physical hardware maintenance burden.
Choose Private Cloud When:
  • Strict strict legal/regulatory sovereignty dictates physical custody of data.
  • Predictable 24/7/365 steady-state load where owned hardware is amortized cheaper.
  • Legacy applications requiring custom bare-metal OS or direct hardware access.
  • Ultra-low sub-millisecond local factory/medical network latency required.

🌍 Region vs. Availability Zone & Egress Economics

M1-2 Slide 32 M1-2 Slide 33
🌐 Region

A separate, independent physical geographic area in the world (e.g., eu-central-1 Frankfurt, us-east-1 N. Virginia). Completely isolated from other regions to contain blast radius. Contains a minimum of 2 or 3 Availability Zones.

🏢 Availability Zone (AZ)

One or more discrete physical data centers with independent power, industrial cooling, and networking within a region. Connected to other AZs in the same region via high-bandwidth, ultra-low-latency private fiber optic links (<2 ms).

💸 The Physics & Economics of Cloud Egress (Slide 33) Exam Trap

Ingress (data flowing INTO the cloud provider) is almost universally FREE. Cloud providers want your data.

Egress (data flowing OUT of the cloud provider to the internet, another region, or on-premises) incurs heavy per-gigabyte bandwidth fees.

• Same AZ data transfer: Usually free or pennies per GB.
• Cross-AZ in same region: Charged at nominal rates (~$0.01/GB both ways).
• Cross-region or Internet egress: Significant billing shock (~$0.05–$0.09/GB). Architect systems to cache data at CDN edge (CloudFront/Cloudflare) to slash egress.

🖥️ Hypervisors, Virtual Hardware Allocation, Overcommitment & Right-Sizing

M1-2 Slides 36–37 M1-2 Slide 38 M1-2 Slide 39 M1-2 Slide 40

Type 1 (Bare-Metal) vs. Type 2 (Hosted) Hypervisors (Slides 36 & 37)

Attribute Type 1: Bare-Metal / Native Type 2: Hosted / Client
Architecture Layer Runs directly on bare-metal physical hardware with no host OS. Runs as an application on top of a general-purpose host OS (Windows/macOS/Linux).
Performance & Overhead Near-native hardware speeds; microsecond I/O scheduling; zero OS bloat. Higher latency; double overhead as guest calls traverse hypervisor then host OS kernel.
Use Case Cloud enterprise data centers (AWS Nitro/KVM, Azure Hyper-V, VMware ESXi). Desktop development & student labs (VirtualBox, VMware Workstation).
What the Hypervisor Allocates to Each VM (Slide 38):
1. vCPU Virtual cores mapped to physical hyperthreaded host CPU execution threads.
2. Memory (vRAM) Dedicated blocks of host physical RAM mapped to guest memory pages.
3. Virtual Disk File representing a hard drive (VHD, VMDK, or network-attached SAN block).
4. vNIC Virtual network interface card assigned its own unique virtual MAC address.
Overcommitment / Over-provisioning Slide 39

Allocating more total virtual resources (especially vCPU and disk) across all VMs than physical hardware actually possesses. Works because average server utilization is ~10–20%.

Danger: Overcommitting RAM can cause hypervisor memory ballooning and disk swapping, collapsing performance.
Right-Sizing Slide 40

The continuous engineering practice of analyzing real-time CPU, RAM, network, and storage performance metrics to match instance sizes to actual workload demand.

Benefit: Downgrading an idle 8-vCPU instance to 2-vCPU immediately saves 75% on compute billing with zero loss in performance.

⚡ VM Deployment Components, Storage Tiers, Pricing & Autoscaling

M1-2 Slide 41 M1-2 Slide 42 M1-2 Slide 43 M1-2 Slide 44
What You Select When Launching a Cloud VM (Slide 41):
1. Machine Image OS template (AMI, Ubuntu, Windows Server 2022).
2. Instance Size Family ratio of vCPUs to RAM (e.g. t3.micro, c6g.2xlarge).
3. Network & Rules VPC, target subnet, and Security Group port rules.
4. Storage Volume Root disk size and IOPS tier (EBS gp3, io2).
5. Login Key Asymmetric SSH public key injected at launch for secure access.
Local Disk (Ephemeral / Instance Store)

Physically inside the host chassis. Blazing fast NVMe speed. Ephemeral: Data is permanently destroyed if the VM is stopped or host fails. Use only for scratch/swap.

Network Disk (Persistent Block Storage / EBS)

Dedicated network volume (SAN/NVMe-oF). Persistent: Retains data independently when the VM stops. Can be detached and attached to another instance in the same AZ.

Snapshot

Point-in-time incremental backup of a block storage volume stored in highly durable object storage (S3). Used to restore disks or clone AMIs across regions.

Compute Instance Pricing Models (Slide 43):
On-Demand

Pay by the second with zero long-term commitment. Highest hourly rate. Best for unpredictable, newly launched, or short-term workloads.

Reserved / Savings Plans

Commit to 1 or 3 years of steady-state usage. Huge discount (30% to 72% off). Best for databases and core 24/7 web application servers.

Spot Instances

Bid on spare cloud capacity at up to 90% discount. Can be terminated with 2 minutes notice when capacity is reclaimed. Best for batch rendering and fault-tolerant CI/CD jobs.

Autoscaling Architecture (Slide 44):

An Autoscaling Group (ASG) maintains application availability by automatically adding or removing VM instances based on defined scaling policies. It enforces three core thresholds:

Min Capacity: Lower floor (e.g. 2 instances) Desired Capacity: Target steady state (e.g. 4 instances) Max Capacity: Cost runaway ceiling (e.g. 10 instances)

🚀 Migration Terminology & Strategic Drivers

M3 Slide 5 M3 Slide 6
Cloud Migration

The end-to-end process of transitioning digital business operations, applications, databases, and IT assets into cloud computing environments.

Workload

A discrete, identifiable collection of code, data, and compute resources that deliver business value (e.g., e-commerce storefront, payroll system).

Source & Target

Source: Existing on-prem or legacy environment. Target: The destination cloud provider account and region.

Cutover

The precise, coordinated moment when production user traffic is redirected from the source environment to the newly migrated target system.

Rollback

The predetermined, pre-tested emergency procedure to revert traffic back to the source system if fatal defects emerge during cutover.

📈 Reasons to Move to the Cloud (Slide 6)
  • Business Agility: Launch new product features in hours instead of waiting months for server procurement.
  • Elastic Scale: Automatically handle holiday shopping traffic spikes without purchasing permanent idle hardware.
  • Global Footprint: Deploy applications near international users across 30+ geographic regions in clicks.
  • Modern Managed Services: Access AI/ML models, serverless functions, and auto-tuning databases out of the box.
  • Hardware Refresh Avoidance: Eliminate $2M+ periodic SAN and server chassis replacement cycles.
🛑 Reasons to Stay On-Premises (Slide 6)
  • Regulatory & Data Sovereignty: Laws strictly requiring military or banking records to remain in physical company custody.
  • Extreme Legacy Architecture: Specialized mainframes (e.g. IBM AS/400) or bespoke hardware that cannot be virtualized.
  • High Steady-State 24/7 Load: Predictable, continuous compute where amortized CapEx hardware is cheaper than continuous hourly cloud bills.
  • Ultra-Low Physical Latency: Real-time industrial manufacturing sensors requiring sub-millisecond local fiber response.

🎯 The 7 R's Migration Strategies & Rehost vs. Refactor

M3 Slide 11 M3 Slide 12
Strategy Industry Alias Action & Architectural Impact Effort / Value
1. Rehost "Lift and Shift" Move virtual machines exactly as-is into cloud VMs with zero code or architecture modifications. Fastest / Low ROI
2. Replatform "Lift, Tinker, Shift" Make minor targeted optimizations to adopt managed cloud components (e.g., replace self-hosted MySQL with Amazon RDS) without rewriting core app logic. Moderate / Medium ROI
3. Refactor "Re-architect" Completely redesign and rewrite the application using cloud-native paradigms: microservices, serverless functions, event-driven queues, auto-scaling DBs. Highest / Maximum ROI
4. Repurchase "Drop and Shop" Abandon the legacy application entirely and purchase an off-the-shelf SaaS replacement (e.g., moving on-prem Siebel CRM to Salesforce). Fast / Low Tech Debt
5. Retire "Decommission" Turn off redundant, dead, or obsolete services uncovered during discovery phase (typically 10–20% of an enterprise portfolio). Immediate 100% Savings
6. Retain "Revisit / Keep" Keep the application on-premises because of regulatory blocks, heavy amortized investment, or pending obsolescence. Zero Migration Cost
7. Relocate "Hypervisor Lift" The 7th "R" added by AWS: Move hypervisor-based workloads directly to a cloud-hosted version of the exact same hypervisor (e.g. VMware Cloud on AWS) with zero configuration changes. Zero OS conversion
Rehost vs. Refactor: Strategic Trade-Off Analysis (Slide 12)
Rehost (Lift & Shift)

• Primary Benefit: Rapid evacuation of a closing data center or expiring lease.

• Downside: Inherits all legacy architectural bugs, monolithic memory leaks, and inefficient OS licensing costs. Misses true cloud elasticity.

Refactor (Cloud-Native Re-architecture)

• Primary Benefit: Maximizes cloud elasticity, auto-scales to zero, lowest ongoing operational compute bills.

• Downside: Very high upfront software engineering cost, high developer skill requirement, and long time-to-market.

🚚 Data Transfer Mechanics, VM Conversions & Cutover Strategies

Online Transfer (Slide 18)

Data streamed over network (VPN, Direct Connect, AWS DataSync). Best for continuous replication and datasets under ~10–20 Terabytes where bandwidth capacity permits timely transfer.

Problems Moving Cloud-to-Cloud (Slide 21) Slide 21

Moving between cloud providers is fraught with obstacles: punitive data egress fees, proprietary API differences, IAM syntax incompatibility, and managed database engine locks (e.g. DynamoDB to CosmosDB).

Cutover Strategies (Slide 22):
Big Bang Cutover

Entire user traffic flipped all at once in a single maintenance window. High risk; no intermediate state. If a fatal defect strikes, full rollback is required.

Phased / Parallel Cutover

Workloads or user cohorts migrated incrementally over weeks. Old and new run simultaneously with dual writes or traffic split. Low risk, but requires complex data synchronization.

🧪 The 6 Mandatory Testing Types & Post-Migration Problems

M3 Slide 23 M3 Slide 25
1. Functional Testing

Verifying application features, API endpoints, and button clicks produce expected outputs without throwing runtime exceptions.

2. Performance & Load

Simulating peak concurrency, measuring latency under stress, verifying autoscaling triggers fire when CPU crosses threshold.

3. Data Validation

Executing cryptographic hash checksums, row-count comparisons, and foreign key audits to prove zero data corruption during transfer.

4. Security Testing

Vulnerability scanning, port audits, IAM permission checks, ensuring no sensitive S3 buckets are left publicly readable.

5. Regression Testing

Ensuring that moving or upgrading one module has not broken existing, unchanged dependent modules elsewhere in the system.

6. User Acceptance (UAT)

Actual business end-users and department leads testing day-to-day operations and formally signing off on operational readiness.

Common Problems Encountered After Migration (Slide 25):
• Zombie Resources & Bill Shock: Orphaned unattached EBS storage volumes, idle Elastic IPs, or forgotten testing clusters continuously billing.
• DNS Caching Delays: Clients still routing to decommissioned on-prem servers due to high pre-migration DNS TTLs.
• Unexpected Latency: Monolithic database queries traversing cross-region VPC links instead of local subnets.
• Misconfigured Security Groups: Inadvertently blocking legitimate application microservice communication ports.

🔄 Project Methodologies, Deployment Strategies & Capacity Limits

M3 Slide 26 M3 Slide 28 M3 Slide 29
Waterfall Migration (Slide 26)

Linear sequential approach. Entire discovery, design, build, and cutover happen in single rigid phases. High risk: defects discovered only at the very end during massive cutover.

Agile Wave Migration (Slide 26)

Workloads grouped into iterative "migration waves" (sprints). A simple pilot app is migrated first to test automation; lessons learned refine subsequent enterprise waves. Highly recommended.

Deployment Strategies (Slide 28):
Blue-Green Deployment

Two identical production environments exist. Blue runs live traffic; Green receives new code. Route 53 / Load Balancer instantly flips 100% traffic to Green. Instant rollback: switch back to Blue if errors spike.

Canary Deployment

New software version deployed alongside old version. Load balancer directs small fraction (5–10%) of live traffic to the canary. If telemetry and error rates remain clean, traffic ramps to 100%.

Rolling Deployment

Instances updated in incremental batches (e.g. 2 at a time). Upgraded instances pass health checks before next batch updates. Zero downtime, but two software versions run concurrently during update.

Cloud Capacity Bottlenecks (Slide 29):
1. Account Limits (Service Quotas): Default ceilings (e.g. max 5 Elastic IPs per region, 20 vCPUs) requiring formal quota increase tickets.
2. Regional Shortages: High-demand GPU instances (A100/H100) or specific instance types temporarily unavailable in an AZ.
3. Network Bandwidth Limits: Maximum throughput per EC2 instance type (e.g. 5 Gbps vs 100 Gbps EFA).

🛡️ Business Continuity (BC), Disaster Recovery (DR) & Recovery Metrics

M3 Slide 30 M3 Slide 31 M3 Slide 32
Business Continuity (BC) — Slide 30

The broad strategic business plan that ensures essential business operations, customer communications, executive leadership, and supply chains continue functioning during and immediately after a catastrophic event.

Disaster Recovery (DR) — Slide 30

A technical sub-discipline of BC focused specifically on recovering and restoring IT infrastructure, database integrity, networks, and software applications following an outage.

RPO (Recovery Point Objective) Data Loss Dimension

The maximum acceptable age of data loss measured back in time from the moment of disaster. Dictates how frequently backups or replication must occur.

• If RPO = 15 minutes: Backups/CDC must sync at least every 15 minutes.
• If RPO = 0: Synchronous multi-AZ database replication is strictly required.
RTO (Recovery Time Objective) Downtime Dimension

The maximum acceptable duration of system downtime between disaster declaration and full operational restoration. Dictates how fast infrastructure must be recovered.

• If RTO = 2 hours: Automated IaC failover scripts must restore compute within 120 minutes.
• If RTO = 0: Multi-region active-active hot site architecture is required.
Disaster Recovery Site Types (Slide 32):
Site Type Infrastructure State RPO / RTO Cost Profile

⚡ TCP vs. UDP & RFC 1918 Private Addressing

TCP (Transmission Control Protocol) Connection-Oriented

Requires a formal 3-Way Handshake (SYN $ ightarrow$ SYN-ACK $ ightarrow$ ACK) before any data flows. Guarantees in-order delivery, retransmits lost packets, performs flow control (windowing) and checksum integrity.

🧮 CIDR Subnet Math & The 5 Reserved Cloud IP Addresses

M4 Slide 10 M4 Slide 12
Classless Inter-Domain Routing (CIDR) Calculation (Slide 10) Standard Formula
\[ \text{Total Addresses in a } /n \text{ block} = 2^{(32 - n)} \]

In IPv4, the address consists of 32 bits. The /n prefix denotes the number of fixed network bits; the remaining 32 - n bits are available for host addressing.

The 5 Reserved Addresses in Cloud Subnets (Slide 12) #1 Most Tested Exam Rule

In traditional on-premises networking, 2 addresses are reserved (Network and Broadcast). In cloud provider subnets (AWS VPC), exactly 5 addresses are ALWAYS reserved and cannot be assigned to any VM or network interface:

IP Offset in Subnet (Example: 10.0.0.0/24) Reserved Function & Purpose
10.0.0.0 (.0)Network Address: Identifies the subnet boundary itself.
10.0.0.1 (.1)VPC Router / Default Gateway: Internal router interface for the subnet.
10.0.0.2 (.2)DNS Server: AmazonProvidedDNS (Route 53 resolver for VPC queries).
10.0.0.3 (.3)Reserved by Cloud Provider: Dedicated for future internal feature use.
10.0.0.255 (.255)Broadcast Address: Broadcast is unsupported in VPC; reserved.
\[ \text{Usable Cloud Hosts} = 2^{(32 - n)} - 5 \]
• For a /24: $2^8 - 5 = 256 - 5 = $ 251 usable host IPs.
• For a /28: $2^4 - 5 = 16 - 5 = $ 11 usable host IPs.
• Minimum AWS subnet size is /28 (11 usable); maximum size is /16 (65,531 usable).

🛡️ Stateful Security Groups vs. Stateless NACLs

M4 Slide 23 M4 Slide 25
Feature Security Groups (Machine-Level) Network ACLs / NACLs (Subnet-Level)
Scope of Boundary Virtual Interface / Instance level (vNIC). Subnet boundary level (protects entire subnet).
Statefulness STATEFUL: Return traffic is automatically allowed back regardless of inbound rules. Connection tracking table remembers states. STATELESS: Return traffic is NOT remembered. Outbound rules must explicitly permit ephemeral return ports (1024–65535).
Rule Evaluation Evaluates ALL rules before deciding. Supports ALLOW rules only (implicit deny all). Evaluates rules in numerical order (lowest number first, e.g. rule 100 before 200). Stops at first match. Supports both ALLOW and DENY rules.
Critical Cloud Firewall Configuration Mistakes (Slide 25):
• Exposing Admin Ports to the World: Adding Security Group rule allowing TCP port 22 (SSH) or 3389 (RDP) from 0.0.0.0/0. Results in immediate automated brute-force attacks.
• Forgetting Stateless NACL Ephemeral Return Ports: Allowing inbound port 80/443 on a NACL but forgetting to allow outbound ephemeral ports (1024-65535), causing web responses to drop silently.
• Confusing SG with NACL Scope: Blocking a malicious IP in a Security Group using a Deny rule (impossible; SGs do not support Deny rules! Must block via NACL).
• Rule Number Shadowing in NACLs: Placing an Allow rule at number 100 and a Deny rule for a specific IP at number 200; the Allow rule matches first and the Deny is ignored.

🐢 Why Connections Are Slow & The VPN MTU / MSS Clamping Problem

M5 Slide 35 M5 Slide 36
Four Reasons a Working Connection is Slow (Slide 35):
1. Round-Trip Latency (RTT)

Physical distance. Speed of light in fiber optic glass is ~200,000 km/s. A packet traversing Frankfurt to Tokyo takes ~220 ms RTT minimum; cannot be fixed by adding bandwidth.

2. Bandwidth Bottleneck

Link saturation, interface bandwidth throttling, or ISP transit pipe congestion causing queues to fill and bufferbloat.

3. Packet Loss

Dropping even 2% of packets causes TCP congestion control algorithms to slash window size in half and enter exponential backoff retransmissions.

4. Packet Size (MTU Mismatch)

Packets exceeding the link's Maximum Transmission Unit (MTU) get fragmented or dropped if Don't Fragment (DF) bit is set.

Why VPNs Have a Packet-Size (MTU) Problem & MSS Clamping Solution (Slide 36) High-Yield Exam Calculation

Standard Ethernet Maximum Transmission Unit (MTU) is 1500 bytes. When an instance sends a 1500-byte packet into an IPsec VPN tunnel, the VPN gateway adds 50 to 73 bytes of IPsec encryption overhead (ESP header, Initialization Vector, padding, HMAC auth tag, and outer IP header). The resulting packet is 1570 bytes, exceeding the internet's 1500-byte limit!

The Problem: Black Hole Drops

If the host sets the DF (Don't Fragment) bit, the VPN router must drop the packet. If intermediate ICMP "Fragmentation Needed" error messages are blocked by firewalls, the client experiences a silent freeze ("Path MTU Discovery Black Hole").

The Solution: MSS Clamping

The VPN router inspects TCP SYN packets during handshake and automatically reduces the advertised Maximum Segment Size (MSS) from 1460 to 1360–1390 bytes. Hosts send smaller packets; zero fragmentation; zero drops.

\[ \text{Recommended TCP MSS} = 1500 - 40 \text{ (IP+TCP headers)} - 72 \text{ (IPsec overhead)} = \mathbf{1388 \text{ bytes}} \]

💰 Quantitative Risk Formulas (SLE, ARO, ALE) & 4 Risk Responses

M6 Slide 11 M6 Slide 12
Quantitative Risk Analysis Formulas (Slide 11) Guaranteed Exam Math
Single Loss Expectancy (SLE)
\[ \text{SLE} = \text{Asset Value (AV)} \times \text{Exposure Factor (EF)} \]

The total monetary loss suffered each time a single risk event occurs. EF is the percentage of asset value lost (0.0 to 1.0).

Annualized Loss Expectancy (ALE)
\[ \text{ALE} = \text{SLE} \times \text{Annualized Rate of Occurrence (ARO)} \]

The total expected loss per year. ARO is estimated frequency per year (e.g. once every 2 years = ARO 0.5).

Concrete Example: An e-commerce database asset is valued at \$200,000. An outage causes a 25% loss (EF = 0.25). Historical data predicts an outage once every 2 years (ARO = 0.5).
• $\text{SLE} = \$200,000 \times 0.25 = \mathbf{\$50,000}$.
• $\text{ALE} = \$50,000 \times 0.5 = \mathbf{\$25,000 \text{ per year}}$.
Decision Rule: A cloud security control (e.g. multi-AZ standby) costing \$10,000/yr is financially justified because it saves \$25,000/yr in ALE!
The 4 Ways to Respond to a Risk (Slide 12):
1. Mitigate (Reduce)

Implement technical or administrative safeguards (deploying a WAF, patching software, enforcing MFA) to lower probability or impact.

2. Transfer (Share)

Shift financial loss to a third party (purchasing cyber liability insurance or shifting infrastructure patching to a PaaS/SaaS provider).

3. Avoid

Eliminate the risk entirely by ceasing the risky activity (shutting down an insecure legacy feature, refusing to collect credit card data).

4. Accept

Acknowledge the risk and take no action when the cost of mitigation exceeds the expected ALE loss. Must be formally signed off by executive leadership.

How KMS Protects Large Data: Envelope Encryption (Slide 18) Core Architecture Concept

1. GenerateKey KMS uses Customer Master Key to generate: 1) Plaintext DEK; 2) Encrypted DEK.
2. Encrypt Data Application encrypts multi-GB file locally using the Plaintext DEK with AES-256.
3. Wipe Memory The Plaintext DEK is immediately destroyed from memory to prevent extraction.
4. Store Envelope The Encrypted DEK is stored right next to the encrypted file ("in the envelope").

CVSS (Common Vulnerability Scoring System) gives a 0.0–10.0 technical severity score. However, Business Risk considers exposure: a CVSS 9.8 flaw on an isolated offline server with zero route to internet represents lower business risk than a CVSS 7.0 flaw on an internet-facing production payment gateway!

Web Application Firewall (WAF) — Slide 27

Inspects Layer 7 HTTP/HTTPS payloads to stop application exploits: SQL Injection (SQLi), Cross-Site Scripting (XSS), CSRF, and bot scrapers.

DDoS Protection (AWS Shield / Cloudflare) — Slide 27

Mitigates Layer 3/4 volumetric packet floods (SYN floods, UDP amplification) and Layer 7 application exhaustion attacks at edge locations.

Cloud Logging & SIEM / SOAR (Slides 29 & 30):
Audit Logs: CloudTrail / Activity Log recording every API call, identity, and timestamp.
Flow Logs: VPC network packet telemetry (source, destination, port, ACCEPT/REJECT).
SIEM: Centralized ingestion and correlation of logs across all cloud resources to detect attacks.
SOAR: Automated security playbooks that automatically isolate compromised VMs in quarantine SGs.

2. Detect

👤 Identity Types, Authentication Factors & Cryptographic Storage

M7 Slide 6 M7 Slide 9 M7 Slide 10 M7 Slide 12 M7 Slide 13
Human Identities (Slide 6)

Administrators, engineers, employees, and customers logging in interactively via web consoles or CLI sessions using usernames, passwords, and multi-factor authentication (MFA).

Machine / Workload Identities (Slide 6)

Applications, backend microservices, EC2 instances, and CI/CD automation runners authenticating non-interactively using API tokens, TLS certificates, or temporary IAM Roles.

NIST SP 800-63B Password Guidelines (Slide 10): Modern Standard
DO:
  • Encourage long passphrases ($ge 15+$ characters; length beats complexity).
  • Check passwords against dictionaries of known breached passwords.
  • Allow users to paste credentials from password managers.
  • Enforce Multi-Factor Authentication (MFA) on all accounts.
DO NOT:
  • Do NOT force periodic password resets (e.g. every 90 days) without cause; it leads to predictable patterns (Spring2026!).
  • Do NOT enforce arbitrary composition rules (requiring uppercase + number + symbol).
  • Do NOT use knowledge-based security questions ("mother's maiden name").
  • Do NOT place password truncation limits or disable paste functionality.
Salt & Slow Hashing vs. Fast General Hashes (Slide 12)
Cryptographic Salt

A unique, cryptographically random string appended to the password before hashing. Defeats precomputed Rainbow Table attacks; ensures two users with identical passwords yield completely different hashes.

Fast General Hashes (SHA-256)

Never use for passwords! Designed to verify files in microseconds. Attackers with modern GPUs can guess over 10 billion SHA-256 hashes per second.

Slow Adaptive Hashes

Industry Standard: bcrypt, Argon2, PBKDF2, scrypt. They feature configurable work factor loops and memory hardness, forcing expensive CPU/RAM cost per guess.

Multi-Factor Authentication (MFA) Verification Methods (Slides 9 & 13):
1. SMS / Voice Code

Least secure; vulnerable to SIM swapping, cellular SS7 interception, and fake login pages.

2. Authenticator App (TOTP)

RFC 6238 6-digit rolling code generated locally from shared secret seed. Immune to SIM swap, but vulnerable to real-time reverse proxies.

3. Push Approval

One-tap mobile notification. Must enforce Number Matching to prevent "MFA Fatigue" prompt bombing attacks.

4. Security Key / Passkey

FIDO2 / WebAuthn. Hardware cryptographic challenge bound directly to domain origin. 100% phishing-resistant.

📋 IAM Policy Anatomy, Policy Types & RBAC vs. ABAC

M7 Slide 15 M7 Slide 16 M7 Slide 18
The 5 Parts of an IAM Permission Statement (Slide 15):
1. Effect Allow or Deny. Explicit Deny ALWAYS trumps any Allow!
2. Principal The IAM user, role, federated identity, or account receiving permission.
3. Action The exact API call (e.g. s3:GetObject, ec2:RunInstances).
4. Resource The Amazon Resource Name (ARN) targeting the object (arn:aws:s3:::bucket/*).
5. Condition Context rules: required source IP CIDR, MFA active, or TLS version $ge$ 1.2.
Identity-Based vs. Resource-Based Policies (Slide 16) Slide 16

• Identity-Based Policy: Attached directly to a User, Group, or Role. Defines: "What can this user do across the cloud?"
• Resource-Based Policy: Attached directly to a target resource (e.g. S3 Bucket Policy, KMS Key Policy, SQS Queue Policy). Defines: "Who from any account is allowed to access me?"

RBAC vs. ABAC (Slide 18) Slide 18

• RBAC (Role-Based Access Control): Permissions granted based on job titles (e.g. "BillingAdmin"). Leads to "role explosion" as organizations grow.
• ABAC (Attribute-Based Access Control): Permissions evaluated dynamically based on resource and user tags (User.Dept == Resource.Dept). Highly scalable; zero new roles required when adding employees.

🛡️ Cloud Security Traps: SSRF Defense with IMDSv2 & OIDC in CI/CD

M7 Slide 22 M7 Slide 23
Server-Side Request Forgery (SSRF) & IMDSv2 Defense (Slide 22) Critical Cloud Security Topic

Every cloud VM queries a link-local IP (169.254.169.254) for instance metadata. In an SSRF attack, an external attacker tricks a web server into querying this IP and exfiltrating the VM's temporary IAM role credentials!

IMDSv1 Vulnerability

A simple HTTP GET request returned secrets immediately. Open web proxies, WAF bypasses, and simple URL query injections instantly leaked credentials.

IMDSv2 Session Token Defense

Enforces session tokens. Requires an initial HTTP PUT request with custom header X-aws-ec2-metadata-token-ttl-seconds: 21600. SSRF proxies cannot forge custom PUT headers.

Two-Step IMDSv2 Command:
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/MyRole
CI/CD Pipeline Security & Workload Identity Federation (Slide 23)

The Anti-Pattern: Generating permanent IAM user access keys (AKIA...) and storing them inside GitHub Actions secrets. Keys eventually leak or expire.

The Best Practice (Workload Identity Federation via OIDC): GitHub Actions generates a short-lived cryptographic JSON Web Token (JWT) signed by GitHub. The cloud provider STS (Security Token Service) verifies GitHub's signature and exchanges it for a 1-hour temporary IAM role session. Zero permanent credentials stored anywhere!

🌐 Identity Federation, SSO & Standard Protocols (SAML, OIDC, SCIM)

M7 Slide 25 M7 Slide 26 M7 Slide 27
Federated Sign-In Architecture (Slides 25 & 26)

Identity Provider (IdP): Central system authenticating corporate identities (Microsoft Entra ID, Okta).
Service Provider (SP): The cloud provider console (AWS, Azure) trusting the IdP.

1. User Accesses SP User navigates to cloud login URL; SP redirects to corporate IdP.
2. Authenticate at IdP User enters corporate credentials and completes MFA on the IdP login page.
3. Signed Token Issued IdP generates cryptographically signed assertion token back to user's browser.
4. SP Issues Session Browser posts token to SP; SP verifies signature and logs user into console.
Protocol / Standard Format & Foundation Primary Purpose
SAML 2.0 XML-based Enterprise Web Single Sign-On (SSO) between corporate IdPs and cloud management consoles.
OAuth 2.0 HTTP / JSON Tokens Authorization Framework issuing scoped access tokens (e.g. allowing third-party app to read user Google Drive files without seeing password).
OpenID Connect (OIDC) JSON Web Tokens (JWT) Authentication Layer built on top of OAuth 2.0. Used for modern mobile/web login and GitHub Actions cloud federation.
SCIM REST / JSON System for Cross-domain Identity Management: Automates user provisioning and de-provisioning (creating/deleting accounts in SaaS tools when HR adds/terminates employees).

🏛️ Identity Lifecycle Governance & Emergency Access

M7 Slide 28 M7 Slide 29 M7 Slide 30
Joiners, Movers, Leavers (JML) & Privilege Creep (Slide 28):
Joiners Automated onboarding provisioning baseline role permissions via SCIM.
Movers & Privilege Creep Employees changing departments. Must revoke old department permissions; failure to do so causes Privilege Creep (accumulating dangerous excess permissions over time).
Leavers Terminated staff. Automated instant de-provisioning across all cloud accounts to prevent ex-employee backdoor access.
Just-In-Time (JIT) Access

Engineers have zero persistent admin rights. Elevated privileges are requested for approved maintenance windows and auto-expire after 2 hours.

Separation of Duties (SoD)

Critical tasks require 2 distinct individuals (e.g. software engineer cannot approve their own pull request to production).

Break-Glass Account

Emergency cloud root account with extreme MFA (stored in a physical company safe). Used exclusively when corporate IdP is completely down.

Conditional Access Policies (Slide 30):

Evaluates real-time contextual telemetry signals before allowing access:

Signals Evaluated: User role, IP geographic location (flagging "impossible travel" e.g. login from Istanbul then Tokyo 10 min later), device health (MDM compliant / antivirus active), and real-time risk score.
Enforcement Decisions: Allow directly, prompt for Phishing-Resistant FIDO2 MFA, require compliant corporate laptop, or Block access immediately and alert the SOC.
