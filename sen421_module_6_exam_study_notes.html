PART 1

Starting Simple: What Goes Wrong in the Cloud

Slides 3/38 – 5/38

Where We Are & Today's Core Security Question

Slide 3/38

From the Previous Topics:

  • Workloads were migrated, placed in private subnets, and given firewall rules.
  • The cloud network was connected to the office by VPN or a dedicated link.
  • We learned to find what blocks a connection.
Today's Question: Everything works. Customer records, payments, and staff data now live in cloud services we do not own, with selected entry points open to the internet. How do we keep the wrong people out, and how do we know when they got in?

A Comparison You Already Understand: Protecting a House

Slide 4/38
🏠 The House ☁️ The Cloud System
Locks on the doors and windows Firewalls and private subnets
Keys given only to the family Accounts and permissions (next topic)
A safe for valuables Encryption
An alarm and a camera Logs and alerts
A plan: who to call if the alarm rings An incident response plan
Insurance: pays for part of what goes wrong Insurance and contracts: money, not responsibility
🛡️ Core Principle: No single lock is enough. Security is several layers, each covering the others' gaps.

What Actually Goes Wrong

Slide 5/38

Common cloud incidents start with the customer's configuration, credentials, or unpatched software:

Mistake Result
A storage bucket set to "public" Anyone who finds the address downloads the files
A database or SSH port open to 0.0.0.0/0 Automated scanners find it quickly and start trying
An access key written into code pushed to a public repository An attacker runs resources in your account; you receive the bill
Software not updated for months A known, published weakness is used
A machine or program given far more permission than it needs One small hole opens everything
No logs Detecting and investigating the attack become much harder
PART 2

Security Principles

Slides 6/38 – 9/38

What We Protect: The CIA Triad

Slide 6/38
Confidentiality C

Only the right people can read it.

Failure: Customer records downloaded by an outsider.
Controls (C): Encryption and access control
Integrity I

It stays correct and complete: no unauthorized or undetected change, corruption, or destruction.

Failure: An attacker changes the bank account number on invoices.
Controls (I): Hashes, signatures, versioning
Availability A

Authorized users get timely, reliable access.

Failure: The registration system is flooded with fake traffic during registration week, or encrypted by ransomware.
Controls (A): Redundancy, backups, DDoS protection

💡 Exam Rule: For each new control, ask which letter (C, I, or A) it protects.

Shared Responsibility, for Security

Slide 7/38
Security of... IaaS PaaS SaaS
Buildings, hardware, hypervisor Provider Provider Provider
Operating system and its patches You Provider Provider
Network settings and firewall rules You Shared Mostly provider
Application code You You Provider
Your data, who can access it, your settings You You You
Core Takeaway: An illustrative division — each service documents its own. The provider secures the cloud; you secure what you put in it. The last row stays yours in every model: classifying data, sharing it, granting access.

Defense in Depth

Slide 8/38
Physical (provider)
Edge: web app firewall (WAF), DDoS protection
Network: subnets and firewall rules
Machine: hardening and patches
Application and access
Data: encryption

Place several layers between an attacker and the data.

  • Each layer stops some attacks.
  • When one layer fails — and one will — the next can still stop or slow the attacker.
  • Layers are not fully independent: one stolen admin credential can open several at once.
👁️ Across all layers: logging and monitoring, so a failure is noticed.

Least Privilege, Zero Trust, and Attack Surface

Slide 9/38
Least privilege

Every person, machine, and program gets only the access it needs, only for as long as it needs it. You met this with firewall rules; in the next topic it applies to accounts.

Zero trust

No request is trusted because of where it comes from or who owns the network. Each request is checked on identity, device, and context — usually through tokens and sessions, not repeated password prompts.

Attack surface

Everything an attacker could try: open ports, public addresses, accounts, software. Smaller means fewer openings.

🏰 Why Zero Trust Fits the Cloud (Castle Model vs. Cloud Model)

The old model was a castle: strong walls, everyone inside trusted. In the cloud there is no single wall — staff work from home, systems talk across networks and providers. Trust has to be checked at every door, not only at the gate.

PART 3

Risk: Deciding What is Worth Protecting

Slides 10/38 – 12/38

Threat, Vulnerability, Risk

Slide 10/38
  • Threat — someone or something that could cause harm: a criminal group, a careless employee, a flood.
  • Vulnerability — a weakness a threat could use: a missing patch, a weak password, a wrong rule. (An open port is exposure; it matters if what listens there is weak.)
  • Risk — how likely harm is, and how bad it would be. A common model:
risk = likelihood × impact
Security costs money: You cannot remove every risk. Prioritize controls by expected loss, legal duties, safety, and how much risk the organization accepts — not only by what the asset would cost to replace.

Putting a Number on Risk: SLE, ARO, and ALE

Slide 11/38
SLE (single loss expectancy)

What one incident costs (exposure factor = the share of the value lost).

SLE = asset value × exposure factor
ARO (annual rate of occurrence)

Expected incidents per year.

Once in 10 years ➔ ARO = 0.1
ALE (annual loss expectancy)

Expected monetary loss per year.

ALE = SLE × ARO
🧮 Worked Example: A Customer Database (Slide 11/38)
  • Before control: Value = $4,000,000, half lost in a breach (EF = 0.5) ➔ SLE = $2,000,000.
  • Expected once in 10 years (ARO = 0.1) ➔ ALE = 2,000,000 × 0.1 = $200,000 a year.
  • With control: A control costing $50,000 a year cuts the rate to once in 50 years (ARO = 0.02) ➔ ALE = 2,000,000 × 0.02 = $40,000 a year.
  • Decision: Saving = $160,000 a year ($200,000 − $40,000), for $50,000. Worth it — net gain $110,000 a year.

Note: Illustrative estimates; same loss each time; yearly control cost; no discounting.

Four Ways to Respond to a Risk

Slide 12/38
Response Meaning Cloud example
Mitigate Reduce likelihood or impact Encrypt the database; close the port
Transfer Someone else carries part of the financial cost, with exclusions Cyber insurance; a contract that makes a supplier pay for its failures
Avoid Stop the risky activity Do not store card numbers at all; use a payment provider
Accept Knowingly live with it, and write it down A test system with no real data, kept with baseline controls only
⚠️ Exam Distinction: "Accept" is a decision made and recorded by someone with the authority to make it — not the same as ignoring the risk.

Encryption and Keys

Slides 13/38 – 19/38

Three States of Data

Slide 13/38
State Example How it is protected
At rest Stored on a disk, in a database, in a storage bucket Disk, database, and storage encryption — often a default or one setting (check each service)
In transit Moving between browser and server, or server and database TLS (HTTPS), VPN tunnels
In use In memory while a program works on it Hardest; "confidential computing" runs code in hardware-protected, verifiable (attested) environments
⚠️ What Encryption at Rest Protects Against (and What It Doesn't): Many services now encrypt data at rest by default. That protects against a stolen disk, but NOT against someone using valid access: for them, the data is decrypted automatically. Authorization still decides.

Two Kinds of Encryption, and Hashing

Slide 14/38
Feature Symmetric Public-key (asymmetric) Hashing
Keys One shared secret key A key pair: public and private No key
What it does Encrypts and decrypts Three different jobs: encryption to a key holder, key agreement, digital signatures A fixed-size, one-way fingerprint
Speed Fast Slow Fast
Used for Bulk data: disks, files, databases, TLS traffic Setting up keys, certificates, signing Detecting changes — if the reference hash is trusted
Examples AES RSA; elliptic-curve schemes (ECDH, ECDSA) SHA-256
Password Hashing Rule: Passwords are never stored with a plain fast hash such as SHA-256: use a slow, salted password-hashing scheme (Argon2id, bcrypt) — next topic.
How TLS 1.3 Combines Them: A key agreement, authenticated by the certificate's signature, sets up keys; symmetric encryption protects the data.

How Strong is "Strong"?

Slide 15/38

Suppose a computer tries a trillion (10^12) keys every second against a sound cipher with a randomly chosen key. Time to try every key (on average, half of it):

Key length Possible keys Time to try them all
56 bits (old DES) 2^56 ≈ 7.2 × 10^16 about 20 hours
128 bits (AES-128) 2^128 ≈ 3.4 × 10^38 about 1.1 × 10^19 years
256 bits (AES-256) 2^256 ≈ 1.2 × 10^77 about 3.7 × 10^57 years

The universe is about 1.4 × 10^10 years old. Each extra bit doubles the work. (These are symmetric key lengths; RSA and ECC keys are sized differently.)

🔓 So How is Encrypted Data Stolen?

Rarely by breaking modern encryption. Attackers steal the key, use an account that is allowed to decrypt, or exploit a flaw in how encryption is used. Protecting keys and access matters more than choosing between AES-128 and AES-256.

Encryption in Transit: TLS and Certificates

Slide 16/38
  • TLS (transport layer security) encrypts traffic between two programs; HTTPS is HTTP inside TLS. Use TLS 1.2 or 1.3, and turn older versions off.
  • A certificate lets the client check that the server holds the private key for www.example.com, vouched for by a certificate authority (CA) the client trusts. It says nothing about whether the site is honest.
  • Certificates expire. After that, new connections fail validation — for every client at once.
📅 Recent Change: Publicly Trusted TLS Certificate Maximum Lifespan (Agreed in April 2025)
From March 15, 2026
At most 200 days
From March 15, 2027
At most 100 days
From March 15, 2029
At most 47 days
(about 8 renewals a year)

Existing certificates keep their dates; internal (private) CAs set their own rules. Renewal must be automated.

Who Holds the Keys?

Slide 17/38
Option (AWS names) How it works Trade-off
Provider-owned keys
(AWS owned)		 The provider creates and uses the key inside its own service; you never see it No effort; no control and no key-use records for you
Provider-managed keys
(AWS managed)		 A key in your account's key management service (KMS), created for one service and rotated by the provider Key use is logged and visible; you cannot change its policy or disable it
Customer-managed keys A KMS key you create and control: who may use it, rotation, disabling, deletion Use is logged; disabling blocks new decryptions (cached data keys may work briefly)
Dedicated hardware or external keys The key is held in a dedicated hardware security module (HSM) or outside the provider Most control, most cost and work; lose the key and the data is gone
Provider Service Names: AWS KMS and CloudHSM Azure Key Vault and Managed HSM Google Cloud KMS and Cloud HSM

Envelope Encryption: How KMS Protects Large Data

Slide 18/38
KMS key
(key-encryption key;
never leaves KMS)
encrypts ───►
Data key
(per object, file, or disk — varies)
encrypts ───►
Your data
(gigabytes)
▲ ─ ─ ─ to read: KMS unwraps the data key
Stored together: encrypted data + encrypted data key
  • KMS returns a new data key twice: plain (used in memory, then erased) and encrypted (stored with the data).
  • To read: Send only the small encrypted data key to KMS — never the gigabytes. With permission, the plain data key comes back; every KMS call is logged.
  • Disabling the KMS key stops new unwrapping; plain data keys already in memory keep working until discarded.

Secrets Do Not Belong in Code

Slide 19/38

A secret is anything that grants access: database passwords, access keys, API tokens, private keys.

❌ Wrong

  • Written in the source code
  • In a configuration file stored in Git
  • Shared in a chat message

⚠️ Once pushed to a repository, a secret stays in its history even after you delete the line.

✅ Right

  • Best: no secret at all — the program uses its own workload identity (next topic)
  • Otherwise: kept in a secrets manager, fetched at run time with the program's own permission
  • Rotated automatically where supported — if the program picks up the new value
Provider Names: AWS Secrets Manager Azure Key Vault Google Secret Manager
🚨 If a secret leaks (Exact Order): Revoke it first; then find where it was used, rotate related credentials, fix the cause, and clean it from history.
PART 5

Protecting Data, and What the Law Requires

Slides 20/38 – 24/38

Know Your Data First: Data Classification

Slide 20/38

Data classification: label data by the harm if it were disclosed, changed, or lost — including legal duties — then protect each class accordingly.

Class University example Typical protection
Public Course catalog, news Integrity and availability; confidentiality not needed
Internal Meeting notes, internal procedures Staff access only
Confidential Student grades, staff salaries Encryption, limited access, logging
Restricted Identity numbers, health records All of the above, plus strict approval and monitoring

An example scheme; organizations define their own. You cannot protect everything at the highest level: classification tells you where the effort goes — and it is the first thing any audit asks for.

Using Less of the Real Data

Slide 21/38
  • Collect less — data you never store cannot leak. The strongest control of all.
  • Masking — show only part: **** **** **** 4417. A masked copy can still identify people; test systems should get synthetic or properly de-identified data.
  • Tokenization — replace a sensitive value with a random token; the real value is kept in one separate, heavily protected place. Payment providers work this way. Reversible tokens are still personal data.
  • Data loss prevention (DLP) — tools that scan storage and outgoing traffic for patterns such as identity or card numbers, and warn or block. They catch some leaks, not all.

The Law: KVKK and GDPR

Slide 22/38
🇹🇷 KVKK — Türkiye's Law No. 6698 on the Protection of Personal Data (2016)
  • Applies to personal data processed in Türkiye
  • Requires technical and administrative security measures
  • Breaches go to the Board as soon as possible: within 72 hours of awareness (Board decision); affected people are told too
🇪🇺 GDPR — the EU's General Data Protection Regulation (2018)
  • Applies to EU establishments, and to others (Turkish firms too) that offer goods or services to, or monitor, people in the EU
  • Breaches go to the authority within 72 hours of awareness where feasible, unless unlikely to risk people's rights; high-risk ones also to the people affected
  • Fines up to EUR 20 million or 4% of worldwide annual turnover, whichever is higher
⚖️ Both require security measures appropriate to the risk; encryption and access control are the typical ones. An engineer who designs the storage is making a legal decision.

Where is the Data? Transfers Abroad & Data Sovereignty

Slide 23/38

Choosing a cloud region is also a legal choice. Personal data stored in a region outside Türkiye — Frankfurt, for example — is generally treated as a transfer abroad under KVKK.

Since the 2024 amendment (Law No. 7499), a transfer abroad needs a normal processing condition plus one of:

1. Adequacy decision: An adequacy decision for the destination country.
2. Appropriate safeguards: Most often the Board's standard contract, notified to the Authority within 5 business days of signing — with data subjects able to use their rights there.
3. Incidental cases: One of a few incidental (non-repeated) cases.
Data sovereignty: Data is subject to the laws of the places where it is stored and accessed. The region is not the whole answer: backups, support access, and subcontractors can move data too. Decide before migrating.

Certifications and Audits

Slide 24/38

Providers publish independent audit reports and certificates, for example:

  • ISO/IEC 27001 — an information security management system is in place and audited.
  • SOC 2 — an auditor's report on security controls: Type I at one point in time; Type II over a period (often 6–12 months).
  • PCI DSS — a standard for systems that handle payment card data; compliance is validated by assessment.

Read the scope: which services and regions, which period, and what the report expects the customer to do.

⚠️ What a Provider's Certificate Does NOT Mean

It covers the provider's side of shared responsibility only. A certified provider can host an uncertified, insecure system — yours. Your part of the audit is still your job.

PART 6

Hardening Machines and the Network Edge

Slides 25/38 – 28/38

Host Hardening and Golden Images

Slide 25/38

Hardening: removing everything a machine does not need, and tightening what is left.

  • Remove unused software and services; close unused ports.
  • Change every default password; disable unneeded default accounts — following tested guidance, since some are needed.
  • Turn on the operating system's own firewall and logging.
  • Follow a published checklist such as the CIS Benchmarks, free for common operating systems and cloud accounts.
📀 Golden images

Harden once, save the result as a versioned image, and build every machine from it. To update, rebuild the image with patches, scan it, and replace the machines. They start identical; configuration and data can still drift, so keep monitoring them.

Patching and Vulnerability Scanning (CVE & CVSS)

Slide 26/38
  • Published weaknesses get a CVE (Common Vulnerabilities and Exposures) ID and a CVSS (Common Vulnerability Scoring System) severity score, 0 to 10. Not every weakness has one.
  • Attackers read the same lists, so publication starts a race. A vulnerability scanner compares your machines and images with the lists.
CVSS score Severity A typical patch target
9.0–10.0 Critical Days, faster if exposed to the internet
7.0–8.9 High Within weeks
4.0–6.9 Medium Normal patch cycle
0.1–3.9 Low A planned, risk-based review cycle
0.0 None —
⚠️ CVSS vs. Business Risk: The targets are organizational policy. CVSS measures severity, not business risk: active exploitation, exposure, and other controls can outweigh the score — a "medium" on a public server can beat a "critical" on an isolated one.

Protecting the Network Edge: WAF and DDoS Protection

Slide 27/38

Previous topics: subnets, firewall rules, private connections. Two more layers sit in front of public services:

Web application firewall (WAF)

A layer 7 filter that reads web requests and blocks many known attack patterns, such as SQL injection. It reduces risk; it does not replace fixing the application (parameterized queries).

DDoS protection

Absorbs or filters floods of traffic from many machines (distributed denial of service), which attack availability. It has limits: application-level floods, and the cost of scaling up, can still hurt.

Provider Names: AWS WAF and Shield Azure Web Application Firewall and DDoS Protection Google Cloud Armor
A WAF is software too: It has settings, and wrong settings open holes. In the Capital One breach (2019), a misconfigured WAF running on the bank's own server was the entry point.

Testing Your Own Security

Slide 28/38
Vulnerability scan

Automatic, broad, frequent: "which known weaknesses seem present?" A finding is not proof it can be used.

Penetration test

People try to break in, the way an attacker would: "can the weaknesses actually be used, and how far can they get?"

Configuration review

Tools compare account settings with a baseline: public buckets, open ports, logging switched off.

📋 Before testing in the cloud: Read the provider's testing policy: policies differ, many common tests of your own resources need no prior approval, and all forbid some activities (such as flooding shared services). Agree in writing on targets you own, scope, test types, and limits.
PART 7

Detecting and Responding to Attacks

Slides 29/38 – 33/38

Logs: The Camera of the Cloud

Slide 29/38
Log Answers the question
Audit log Who changed what in the account, and when? (Created a machine, opened a port, deleted a key.) Reads of data often need extra "data event" logging switched on.
Flow logs Summaries of accepted and rejected traffic (connectivity topic)
Operating system logs Who logged in to this machine? What failed?
Application logs What did users and programs do inside the application?
Rules for logs: switch them on before you need them; send them to a separate, protected place with its own permissions; keep clocks synchronized; set retention and an owner; keep secrets and needless personal data out of them.
Audit Log Service Names: AWS CloudTrail Azure Activity Log Google Cloud Audit Logs

From Logs to Alerts & SIEM

Slide 30/38

Nobody reads millions of log lines. Tools read them and raise alerts — signals to investigate, not proof:

  • a login from a new country at 3 a.m.;
  • audit logging switched off;
  • a storage bucket made public;
  • many rejected connections from one address;
  • a sudden jump in the bill — a common sign of a stolen access key used for cryptocurrency mining (billing data often arrives late).

Each alert needs a severity, an owner, and a planned response; tune out false alarms.

SIEM (security information and event management): Collects logs from everywhere and correlates them: three harmless events together may be one attack. Providers also offer threat detection services that learn what is normal for your account.

Incident Response (6-Step Workflow)

Slide 31/38
STEP 1
1. Prepare

A written plan, contacts, tools, and practice, before anything happens.

STEP 2
2. Identify

Is this really an incident? What is affected?

STEP 3
3. Contain

Stop the harm now: isolate the machine, revoke the leaked key. Preserve evidence alongside (snapshots, logs, memory where possible), without delaying urgent containment.

STEP 4
4. Eradicate

Remove the cause: the malware, the backdoor account, the open port.

STEP 5
5. Recover

Rebuild from a clean image or backup, watch closely.

STEP 6
6. Lessons learned

What happened, why, what changes. Without blame, or people hide the next one.

⏱️ Cloud Advantage & Legal Clock: The cloud helps: a suspect machine can be isolated and copied in minutes. Legal deadlines run from when the organization becomes aware of a personal data breach — assess them as soon as that happens.

Case Study: Capital One, 2019

Slide 32/38
Attack Chain Visualization
1. Entry Point
Attacker (former employee of the cloud provider, not the bank) used a misconfigured WAF on the bank's server.
2. Metadata Request
Made the WAF send requests on her behalf to the cloud's internal metadata service.
3. Over-Privileged Role
Returned temporary credentials of a role with far more permission than it needed, including reading storage buckets.
4. Impact & Fine
Credit card application data of ~100M US + 6M Canada people copied out. Fined $80 million.
Slide Review Questions & Direct Connections to Today's Principles:
• Which principles failed? Least privilege (the WAF role could read storage buckets), hardening / configuration review (misconfigured WAF + weak risk assessment before moving to the cloud).
• Shared responsibility duties on the customer's side: Configuring the WAF running on the bank's server, setting IAM role permissions, and protecting customer data.
• Controls that would have limited damage most: Strict least privilege on the WAF's role (no bucket read access), metadata service protection, configuration review, and alerts on unusual bucket reads.

Exercise: Principle/Control at Stake & First Action (All 5 Scenarios + Suggested Answers)

Slide 33/38
1. A student pushes a project to a public repository; it contains the cloud account's access key.
Suggested Answer: secrets — revoke the key first, then check the audit log for its use.
2. The audit log shows logging was switched off at 02:14 last night.
Suggested Answer: detection — treat it as an incident: who did it, from where, and what else changed.
3. A test database holds a full copy of real customer data.
Suggested Answer: data minimization — replace it with synthetic or properly de-identified data, delete the copy.
4. A critical CVE is published for the web server software on the shop's public machines.
Suggested Answer: patching by risk — patch exposed machines first within days; until then, apply the vendor's mitigation (a WAF rule can help for web-borne attacks).
5. A company plans to store Turkish customers' data in a region outside Türkiye.
Suggested Answer: KVKK transfer abroad — map all data flows (storage, backups, support access), find the legal basis (e.g., a standard contract notified within 5 business days), and involve the legal office.

8-Point Lecture Summary

Slide 36/38
  1. Common cloud incidents start with the customer's configuration, credentials, or unpatched software.
  2. The provider secures the cloud; you secure your data, access, and settings in every service model.
  3. Use layers, least privilege, and a small attack surface; trust no request by location.
  4. Spend on security by risk (ALE = SLE × ARO), within what the law requires anyway.
  5. Encrypt at rest and in transit; attackers usually go around encryption, through keys and access.
  6. Keep secrets out of code; automate certificate renewal.
  7. The region is a legal choice; on becoming aware of a personal data breach, assess notification duties at once (72-hour deadlines).
  8. Harden, patch, log, alert, and have a response plan before you need it.
